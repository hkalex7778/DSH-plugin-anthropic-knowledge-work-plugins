# 交付前分析校验（/data-validate-data）

在把分析分享给相关方之前，审查其准确性、方法论与潜在偏差。产出一份置信评估 + 改进建议。统计方法细节（离群值判定、显著性检验）参考 `data-statistical-analysis` 技能。

## 输入形态

被校验的分析可以是：

- 对话中直接贴出的文档 / 报告 / 结论
- 工作区文件（`read` / `grep` 读 markdown、notebook；`.xlsx` 用 `office-xlsx` 技能或捆绑 pandas 读）
- SQL 查询语句及其结果
- 图表及其底层数据
- 一段方法论 + 发现的描述

## 数据获取（无强制连接器）

需要重算数字时：若已在 设置 → MCP 配置数仓 / BI 服务器，直接取数交叉校验；否则请用户上传 CSV/Excel（`@` 引用文件）或贴出查询结果。拿到原始数据后用 `load_workspace_dependencies` 取捆绑 Python，在 `pwsh` 里重算关键指标——**不要只目测，能重算的就重算**。注意捆绑 Python 没有 scipy/statsmodels/duckdb，手写统计见 `data-statistical-analysis`。

## 工作流

### 1. 审查方法论与假设

- **问题设定**：分析回答的是不是对的问题？有没有另一种解读？
- **数据选择**：用的是不是对的表 / 数据集？时间范围合不合适？
- **人群定义**：分析总体定义得准确吗？有没有非预期的排除？
- **指标口径**：指标定义清晰且前后一致吗？和相关方理解的一致吗？
- **基线与对比**：比较公平吗？时间段、cohort 规模、上下文可比吗？

### 2. 跑交付前 QA 清单

逐项过下面的「交付前 QA 清单」，这是本技能的核心。

### 3. 排查常见分析陷阱

对照下方明细清单系统排查：join 炸行、幸存者偏差、不完整周期对比、分母漂移、平均数的平均数、时区错位、选择偏差等。

### 4. 验证计算与聚合

能拿到原始数据就实际重算（pandas）：

- 独立复算几个关键数字
- 核对小计加总 = 总计
- 核对预期处百分比加总 ≈ 100%
- 确认同比 / 环比用了正确的基期
- 确认所有指标的过滤条件一致应用

再用「结果合理性体检」（量级检查、交叉验证、红旗信号）过一遍。

### 5. 审查可视化

分析含图表时检查：

- 坐标轴起点是否合适（柱状图必须从 0 开始）？
- 对比图的刻度是否一致？
- 图表标题是否如实描述内容？
- 有没有会误导快读者的呈现（截断坐标轴、不等间隔、3D 效果扭曲感知）？

### 6. 评估叙事与结论

- 结论是否被展示的数据支撑
- 是否承认了替代解释
- 不确定性传达是否得当
- 建议是否从发现中逻辑推出
- 置信度表述强度是否与证据强度匹配

### 7. 给出改进建议

具体、可执行：补什么分析能加强结论、该注明什么局限、更好的图或框架、相关方会要的缺失上下文。

### 8. 生成置信评级

三档：

- **可直接发** —— 方法论可靠、计算已验证、caveat 已注明。有小的改进建议但无阻塞项。
- **带保留意见发** —— 大体正确，但有必须向相关方传达的具体局限或假设。列出 required caveats。
- **需返工** —— 发现具体错误、方法论问题或缺失分析，分享前必须处理。按优先级列出必改项。

## 输出格式

```markdown
## 校验报告

### 总体判断：[可直接发 | 带保留意见发 | 需返工]

### 方法论审查

### 发现的问题

2. ...
```

## 交付前 QA 清单

分享给任何相关方之前跑一遍。

### 数据质量

- [ ] **来源确认**：确认用了哪些表 / 数据源，是不是这个问题该用的。
- [ ] **新鲜度**：数据够新，注明 as-of 日期。
- [ ] **完整性**：时间序列没有意外断点，分组没有缺失。
- [ ] **空值处理**：关键列空值率查过；空值处理方式明确（剔除 / 填充 / 打标）。
- [ ] **去重**：确认没有因糟糕的 join 或重复源数据导致的重复计数。
- [ ] **过滤条件**：所有 WHERE / 筛选正确，无非预期排除。

### 计算

- [ ] **聚合逻辑**：GROUP BY 覆盖所有非聚合列；聚合粒度与分析粒度一致。
- [ ] **分母正确性**：比率 / 百分比用对了分母，且分母非零。典型事故：分母口径悄悄排除了试用用户，转化率可能被高估约 5pp——发现这类口径差要量化其影响并写进 caveat。
- [ ] **日期对齐**：比较的时间段长度相同；不完整周期已剔除或注明（如「1 月收入 $500K vs 12 月 $800K」但 1 月还没过完）。
- [ ] **join 正确性**：join 类型合适（INNER vs LEFT）；多对多 join 没有把计数撑大。
- [ ] **指标口径**：指标定义与相关方口径一致，有偏差要注明。
- [ ] **小计加总**：该等于总体的部分加总等于总体；不等要解释（如重叠）。

### 合理性

- [ ] **量级**：数字在合理范围。收入不为负，百分比在 0–100% 之间。
- [ ] **趋势连续性**：时间序列没有无法解释的跳变 / 骤降。
- [ ] **交叉对账**：关键数字对得上其他已知来源（仪表盘、历史报告、财务数据）。
- [ ] **数量级**：总收入量级正确，用户数对得上已知口径（MAU/DAU）。
- [ ] **边界情况**：空分组、零活跃期、新实体等边界怎么样？

### 呈现

- [ ] **图表准确**：柱状图零基线；坐标轴有标签；多面板刻度一致。
- [ ] **数字格式**：精度合适；货币 / 百分比格式统一；该加分隔符的加。
- [ ] **标题清晰**：标题讲洞察而非只报指标名；注明日期范围。
- [ ] **caveat 透明**：已知局限与假设显式写出。
- [ ] **可复现**：别人照着文档能重做这份分析（见下方文档模板）。

## 常见分析陷阱（明细）

### Join 炸行（Join Explosion）

**问题**：多对多 join 悄悄放大行数，把计数与求和撑大。

**如何发现**：

```sql
-- 检查 join 前后行数
SELECT COUNT(*) FROM table_a;                                    -- 1,000
SELECT COUNT(*) FROM table_a a JOIN table_b b ON a.id = b.a_id;  -- 3,500 (出问题)
```

**如何防**：join 后必查行数；行数增加就核实关联关系（真是 1:1 或 1:many 吗）；跨 join 数实体时用 `COUNT(DISTINCT a.id)` 而不是 `COUNT(*)`。

### 幸存者偏差（Survivorship Bias）

**问题**：只分析「今天还在」的实体，忽略被删除、流失、失败的。

**示例**：

- 分析「现有用户」的行为，漏掉了已流失用户
- 只看「在用我们产品的公司」，忽略了评估后离开的
- 只研究「成功」结果的性质，不看「不成功」的

**如何防**：下结论前先问「谁不在这个数据集里？」。若加入缺失群体会改变结论，这就是高严重度问题。

### 不完整周期对比

**问题**：用残缺周期对比完整周期。

**示例**：周三检查「本周注册下降」，对比的却是完整的上一周。

**如何防**：过滤到完整周期，或按同号数 / 同星期几对齐比较。

### 分母漂移（Denominator Shifting）

**问题**：分母在期间之间悄悄变化，使比率不可比。

**示例**：转化率「提升」其实是因为「合格用户」的统计方式变了；流失率变动是因为「活跃」定义更新了。

**如何防**：所有对比期间使用同一定义；口径变更必须显式注明变更点和时点。

### 平均数的平均数

**问题**：对预聚合的平均值再取平均，各组规模不同时结果错。

**示例**：

- A 组 100 人，人均收入 $50；B 组 10 人，人均收入 $200
- 错：($50 + $200) / 2 = $125
- 对：加权 (100×$50 + 10×$200) / 110 = $63.64

**如何防**：永远从明细聚合，不要平均「平均值」。pandas 里用 `sum/count` 而不是先 `groupby.mean()` 再 `.mean()`。

### 时区错位

**问题**：不同数据源时区不同导致对不齐（事件 UTC vs 展示本地时间；日汇总截点不同）。

**如何防**：分析前统一到单一时区（建议 UTC），并文档化所用时区。

### 分组中的选择偏差

**问题**：用要测的结果本身定义分组，循环论证。

**示例**：「完成 onboarding 的用户留存更高」——他们本来就是自选的；「重度用户创造更多收入」——他们是因创造收入才成为重度用户的。

**如何防**：用「处理前」特征定义分组，不要用结果定义。

### 其他统计陷阱

- **辛普森悖论**：汇总与分组后趋势方向相反
- **把相关当因果**：没有支撑证据就下因果结论
- **小样本**：样本量不足以支撑结论
- **离群值过度拉偏均值**（该用中位数吗？→ 用 `data-statistical-analysis` 的 IQR/z-score 方法查）
- **多重检验 / 挑显著结果**
- **前视偏差**：用未来信息解释过去
- **精挑时间窗口**：区间选择偏向某个叙事

## 结果合理性体检

### 量级检查

每个关键数字都要过「嗅觉测试」：

| 指标类型 | 检查 |
|---|---|
| 用户数 | 与已知 MAU/DAU 对得上吗？ |
| 收入 | 与已知 ARR 量级相称吗？ |
| 转化率 | 在 0–100% 之间？和仪表盘对得上吗？ |
| 增长率 | 环比 50%+ 现实吗，还是数据问题？ |
| 平均值 | 结合分布形态看合理吗？ |
| 百分比 | 各分组占比加总 ≈ 100% 吗？ |

### 交叉验证技术

1. **同一指标两条路径算两遍**，看是否一致
2. **抽查个体记录**：挑几个具体实体手工追数据
3. **对已知基准**：公开仪表盘、财务报告、既往分析
4. **倒推**：若总收入是 X，人均收入 × 用户数约等于 X 吗？
5. **边界检查**：过滤到单日 / 单用户 / 单类别时，微观结果讲得通吗？

### 需要追查的红旗信号

- 任何环比变化 > 50% 且无明显原因
- 计数 / 求和恰好是整数（可能是过滤器或默认值问题）
- 比率恰为 0% 或 100%（可能数据不全）
- 结果完美证实假设（现实通常更脏）
- 不同期间 / 分组数值完全相同（查询可能忽略了一个维度）

## 可复现性文档标准

### 分析文档模板

任何非平凡分析都应包含：

```markdown
## 分析：[标题]

### 问题
[要回答的具体问题]

### 数据源
- 表：[schema.table_name]（截至 [日期]）
- 文件：[文件名]（来源：[从哪拿到的]）

### 定义
- [指标 A]：[精确计算方式]
- [分组 X]：[ membership 判定方式]
- [时间段]：[起] 至 [止]，[时区]

### 方法
1. [步骤 1]
2. [步骤 2]

### 假设与局限
- [假设 1 及其合理性]
- [局限 1 及其对结论的潜在影响]

### 关键发现
1. [发现 1 + 支撑证据]

### SQL / 代码
[用到的全部查询，带注释]

### Caveats
- [读者据此行动前需要知道的事]
```

### 代码注释标准

可能复用的 SQL / Python 开头写清：分析目的、作者、日期、数据源、最后验证日期（如「结果与仪表盘误差 < 2%」）、假设（如「活跃 = 当月至少 1 次事件」「排除 is_internal」「全 UTC」）、输出形态。在 DSH 里把查询和处理脚本存成 `.sql` / `.py` 文件（用 `write`），不要只留在对话里。

### 分析的版本管理

- 查询与代码进版本控制（git）或共享文档
- 注明所用数据快照日期
- 用新数据重跑时，记录变了什么、为什么
- 周期性分析链接历史版本便于趋势对比

## 示例请求

- 「这份季度收入分析发给管理层之前帮我校验一下：[分析]」

## 提示

- 任何高风险汇报或决策前先跑本技能
- 再快的分析也值得花一分钟体检——它可能保住你的信誉
- 校验出问题就修，修完再校验一轮
- 把校验报告和正文一起发出去，能为相关方建立信心
